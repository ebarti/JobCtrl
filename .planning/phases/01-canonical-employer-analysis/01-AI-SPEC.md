## 1. System Classification

**System Type:** Structured Data Extraction via Multi-Model Agent Ensemble (Hybrid — extraction + light content generation for the role narrative)

**Description:**
A single-user, local-first step that reads one persisted job-description snapshot and produces a canonical, inspectable "ideal candidate" employer analysis: role framing + inferred seniority + an ideal-candidate narrative; requirements classified must-have vs nice-to-have with a 0–1 priority weight; and reasoned keywords each tied to a quoted job-description evidence span (literal substring) and linked to the requirement they support. It runs through **three agent SDKs in parallel — Claude Agent SDK + Codex SDK + Google Antigravity (Gemini) SDK** (see Section 3) — whose drafts are merged (cross-model agreement + literal-substring evidence validation) and reconciled by a synthesizer pass into one canonical record. "Good" = every claim traces to a real JD span, must/nice + priority reflect what the employer actually wants, the result is stable across runs (cache-backed), and both models' contributions + their agreement are persisted as audit data. It replaces the flakey `_extract_job_keywords` heuristic and becomes the single source of truth driving all downstream resume tailoring.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. **Fabricated grounding** — a keyword or requirement whose quoted evidence span is NOT a literal substring of the persisted JD snapshot (hallucinated source). This is the cardinal failure; it must be rejected deterministically, not trusted from the model.
2. **Silent partial ensemble** — one SDK errors, times out, or returns malformed output and is quietly dropped, yet the analysis is presented at full confidence. A degraded/partial ensemble must be surfaced in the audit trail, never masked.
3. **Unstable / non-reproducible output** — the same job snapshot yields a materially different requirement/keyword set on re-tailor (defeats ANALYSIS-05 and user trust), or the snapshot+version cache is bypassed and the analysis is silently re-reasoned and drifts.
4. **Misclassified priority** — must-have vs nice-to-have inverted, or priority weights miscalibrated, so downstream tailoring spends scarce resume space on the wrong requirements.
5. **Killed mid-run** — the analysis is aborted by a wall-clock timeout or turn cap (forbidden — D-19; only cooperative cancellation may stop it), losing work and corrupting the cache/version state.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Recruiting / hiring (talent acquisition) — specifically job-description interpretation for candidate-side resume tailoring. Adjacent to HR-tech / ATS and the regulated domain of employment (EEO).

**User Population:** A single job seeker who is also the operator and sole beneficiary of the tool. The output is consumed not by the user directly but by the *downstream tailoring engine* (and, eventually, the user inspecting the audit trail in Phase 5). The "domain experts" whose judgment defines quality are the practitioners who professionally read job descriptions for a living: technical recruiters, hiring managers, technical interviewers, and career/resume coaches. The end-of-chain audience the tailored resume must satisfy is a recruiter/ATS screening for a specific role.

**Stakes Level:** High (for a single-user personal tool). The output is not life-or-safety critical, but it is the *single source of truth* that steers every downstream tailoring decision (D-20, ANALYSIS-04). A wrong must-have/nice-to-have call or a hallucinated requirement does not just produce a bad sentence — it systematically misdirects scarce résumé real estate across the entire application, lowering the user's real interview odds, and (because auditability is the product's core value) it poisons the trust contract that every displayed claim traces to real evidence. Misjudged requirements compound silently across many jobs.

**Output Consequence:** The analysis chooses which requirements the résumé emphasizes, how résumé space is rationed (priority weights), what seniority register the résumé adopts, and which keywords are surfaced. Acted on, it directly shapes the user's submitted applications — and downstream, what a recruiter screens and what an ATS matches. A fabricated requirement can induce the tailoring engine to invent or over-claim experience (colliding with the never-fabricate trust floor, CONTROL-01/03); an inverted must/nice call wastes the most valuable résumé lines on the wrong thing.

### What Domain Experts Evaluate Against

<!-- Domain-specific rubric ingredients — practitioner language, not AI jargon. -->

```
Dimension: Must-have vs nice-to-have discrimination
Good (recruiter accepts): Genuine deal-breakers (the hard gates a recruiter would actually reject on — e.g., "5+ years Python", "active security clearance", a required degree/license) are tier=must_have; "preferred", "bonus", "a plus", "ideally", "familiarity with" items are tier=nice_to_have. The split matches how the requirement is phrased AND how the role functions.
Bad (recruiter flags): Aspirational wishlist items promoted to must-have, or a true gate demoted to nice-to-have. Treating a long qualifications list as if every line is mandatory — recruiters know posted qualifications are aspirational, not literal gates (the "men apply at 60%, women at 100%" gap). Mistaking "preferred" for "required".
Stakes: Critical
Source: Recruiter/hiring-manager practice; HBR "Why Women Don't Apply Unless 100% Qualified" (listed qualifications are aspirational, not strict gates).
```

```
Dimension: Evidence fidelity (quote-first grounding)
Good (recruiter/coach accepts): Every keyword and requirement is tied to a quoted span that a reader can find verbatim in the posting; the analysis says what the JD says.
Bad (recruiter/coach flags): A requirement or keyword the JD never states (e.g., inferring "must know Kubernetes" from a generic "cloud experience" line), a paraphrase passed off as a quote, or an evidence span that does not literally appear in the posting. "Where did you get that from?" has no answer.
Stakes: Critical
Source: Repo auditability discipline (every displayed claim has an explicit source of truth, CLAUDE.md); ANALYSIS-03; resume-coaching practice ("tailor to what the posting actually asks").
```

```
Dimension: Priority/weighting realism
Good (recruiter accepts): Within must-haves, the core competency the role is really hired for (the thing the team is missing) carries the top weight; routine/table-stakes items rank lower. Weights reflect what a hiring manager would screen on first, not posting word-count or order.
Bad (recruiter flags): Flat weights, or weights driven by repetition/keyword frequency, or over-weighting a buzzword that appears often but isn't the job's center of gravity. Trivia weighted equal to the headline competency.
Stakes: High
Source: Hiring-manager screening practice; ANALYSIS-02 (spend résumé space on what matters most).
```

```
Dimension: Seniority inference
Good (recruiter accepts): Inferred level matches the signals — scope/ownership language, years-of-experience bands, leadership vs. execution verbs, comp/title cues — and matches how a recruiter would slot the req (IC vs lead, junior/mid/senior/staff).
Bad (recruiter flags): Reading a senior role as junior (or vice versa) because it over-indexed on one cue (e.g., a single tool name) and ignored scope/ownership language; flattening a "lead/principal" posting to a generic mid-level read. Drives the wrong résumé register downstream.
Stakes: High
Source: Technical-recruiter / hiring-manager leveling practice.
```

```
Dimension: Reading the subtext / implicit requirements without inventing
Good (recruiter accepts): Captures the genuinely-implied core need a seasoned reader infers (e.g., "wears many hats / early team" implies ownership and ambiguity-tolerance) AND captures unstated-but-clearly-meant must-haves — while keeping each tied to the JD language that implies it. Distinguishes signal from boilerplate.
Bad (recruiter flags): Two opposite errors. (a) Hallucinating subtext with no anchor in the text (pure invention). (b) Mistaking boilerplate for signal — treating "fast-paced environment", "wear many hats", "passionate", "rockstar", EEO/benefits statements, or legal disclaimers as real requirements. Missing the core competency while cataloguing trivia.
Stakes: High
Source: Recruiter/hiring-manager reading practice; resume-coaching guidance on ignoring filler.
```

```
Dimension: Keyword signal vs ATS keyword-stuffing
Good (recruiter/ATS-ops accepts): Keywords are the genuine skills/tools/qualifications the role screens on, each tied to a real JD span and to the requirement it supports (requirement_ref). A coherent, deduplicated set a human would recognize as "the skills for this job".
Bad (recruiter/ATS-ops flags): A bloated bag of every noun in the posting, near-duplicate variants padded to "maximize match", soft-skill filler and buzzwords elevated to keywords, or keywords with no parent requirement and no evidence. Optimizing for a match-score rather than fidelity — the path to robotic, human-rejected résumés.
Stakes: High
Source: ATS/recruiting-ops practice; project Out-of-Scope explicitly forbids keyword-stuffing-to-maximize-score and single "ATS score" outputs (REQUIREMENTS.md).
```

### Known Failure Modes in This Domain

- **Boilerplate-as-requirement.** Treating filler ("fast-paced", "wear many hats", "rockstar/ninja", "passionate self-starter") or non-requirement sections (EEO statement, benefits, "about us", legal disclaimers) as real requirements or keywords. These are the most common false positives a recruiter would instantly flag, and they crowd out the real signal.
- **Must/nice inversion and wishlist inflation.** Promoting "preferred/ideally/a plus" items to must-have, or demoting a true gate (clearance, license, hard YOE bar) to nice-to-have — then over-spending résumé space on the wrong tier downstream. Recruiters know the posted qualifications list is aspirational; a literal reading misreads the real gates.
- **Hallucinated requirements / over-specification.** Inventing a concrete requirement the JD never states (e.g., a specific framework, certification, or YOE number) by over-inferring from vague language. This is the domain face of the fabricated-grounding cardinal failure and directly risks inducing résumé over-claiming downstream.
- **Seniority misread.** Anchoring level on a single salient token (a tool, a buzzword) instead of scope/ownership/leadership signals — slotting a staff/lead role as mid, or a junior role as senior — sending the wrong register into tailoring.
- **Missing the center of gravity while cataloguing trivia.** Producing a complete-looking list that captures peripheral nice-to-haves and keywords but under-weights or omits the one core competency the role is actually hired for.
- **Keyword-stuffing optimization.** Maximizing keyword count/coverage rather than fidelity — padding near-duplicates and soft-skill filler — which the project explicitly rejects as it produces gameable scores and human-rejected résumés.

### Regulatory / Compliance Context

Hiring is a regulated-adjacent domain. This phase produces a *candidate-side reading of a posting* (it does not screen applicants, make hiring decisions, or process protected attributes), so direct EEO liability is low — but the fairness norms shape what "good analysis" means and what the system must NOT do:

- **No inference or use of protected attributes (EEO / Title VII / ADEA / ADA).** The analysis must never infer, surface, or weight a candidate or "ideal candidate" attribute tied to a protected class — age, sex/gender, race, national origin, religion, disability, pregnancy, genetic info. Phrases like "recent college graduate", "digital native", "young/energetic team", or gendered language in a posting are EEO red flags, not requirements to satisfy; the system must not convert them into requirements or keywords (the EEOC treats such ad language as evidence of unlawful preference).
- **Job-relatedness / disparate-impact lens.** EEOC guidance: requirements must be "job-related and necessary to the business"; neutral criteria with a disproportionate effect on protected groups are suspect. This reinforces the must-have/nice-to-have rubric — flagging an inflated must-have (e.g., a degree requirement not truly needed) is the fairness-aware reading, not just the accurate one.
- **Honesty / no-fabrication norm (downstream).** The analysis feeds tailoring; producing fabricated requirements that pressure the résumé to over-claim collides with the never-fabricate trust floor (CONTROL-01/03) and with basic application-honesty expectations.
- **Data sensitivity (local-first).** Posting snapshots and the user's profile/application data are sensitive per repo policy; analysis stays local, no new external data sharing, no key management (D-04). No GDPR/CCPA processing-of-others'-data concern at single-user scope, but the audit trail (per-model drafts, agreement) is sensitive user data and must not leak.

## 2. Framework Decision

**Selected Framework:** Agent-SDK Ensemble — **Claude Agent SDK + Codex SDK + Google Antigravity (Gemini) SDK** (3 legs; the Google/Antigravity leg was wired 2026-06-09 via the real `google-antigravity` SDK, working reference in `~/Github/mestre`, see Section 3), run in parallel and reconciled by **merge + synthesize** (parallel drafts → cross-model agreement + literal-substring evidence validation → synthesizer reconciliation pass; synthesizer = Claude Agent SDK per CONTEXT D-07). **LOCKED** by the user (CONTEXT.md D-01..D-07); confirmed, not selected.

**Version:** To be pinned by `gsd-ai-researcher` in Section 3 (Installation) for each of the three SDKs. Hard rule: all NEW AI runs through agent SDKs — never raw model APIs / never the legacy httpx `jobhunter.llm.LLMClient`.

**Rationale:**
A quality-first, fully auditable employer-analysis step is the case for a multi-model agent-SDK ensemble rather than a single raw-API call. Each SDK contributes an independent structured draft; running Claude, Codex, and Antigravity in parallel surfaces cross-model agreement/disagreement that becomes first-class persisted audit signal — directly serving the repo's auditability discipline (every displayed claim has an explicit source of truth). A merge-and-synthesize pass (itself an agent-SDK call) unifies the drafts while a deterministic grounding validator enforces that every keyword's quoted evidence is a literal substring of the persisted JD snapshot, eliminating the fabrication mode the old `_extract_job_keywords` heuristic invited. Because the ensemble is stochastic, reproducibility (ANALYSIS-05) is delivered by a snapshot-hash + prompt/SDK-set-version cache contract (compute once, persist, reuse) rather than determinism — which also satisfies the re-tailor reuse requirement (ANALYSIS-06). Agent SDKs give the structured-output, cancellation, and session-auth posture the project standardized on, consume already-present credentials with no new key management, and align with the in-repo `infrastructure/apply/claude_code_cli.py` precedent. With cost/latency declared no object and quality the sole objective, cross-model triangulation buys maximal extraction accuracy and a defensible audit trail.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Portable JSON-Schema + validator re-ask over existing httpx `LLMClient` | Project-level directive moves all NEW AI off the hand-rolled httpx transport onto agent SDKs (D-01); a single-model schema path also forfeits the cross-model agreement signal that is the whole quality rationale. |
| Single Anthropic Messages adapter only (Claude alone) | One model gives no agreement/disagreement audit signal; the explicit goal is "mix 3 diverse models to get better data," quality the only objective, cost no object (D-03, D-18). |
| Stay on Gemini-compat default (`gemini:gemini-3.5-flash`) | Same single-provider + raw-API limitations; superseded by the agent-SDK / ensemble stance (D-05). |
| Heavyweight orchestration framework (LangChain / LangGraph / CrewAI) | Overkill + abstraction overhead for a 3-call parallel-then-reconcile chain; would fight the existing hexagonal `LlmPort` + Temporal control flow. Fallback if an SDK proves non-viable: degrade to a 2-SDK ensemble before ever reverting to a raw-API single-model path. |

**Vendor Lock-In Accepted:** Partial — intentionally multi-vendor (Anthropic + OpenAI + Google). Each SDK is provider-locked individually, but the ensemble deliberately hedges across all three; diversity is the design goal, not a liability. If one SDK becomes unavailable, degrade to a 2-SDK ensemble (keep merge+synthesize) — the ensemble + agent-SDK posture is the locked invariant.

### SDK 1 — Claude Agent SDK (Anthropic, Python) — also the synthesizer (D-07)

**Installation**
```bash

pip install claude-agent-sdk
# uv (this repo): add to workers/automation
uv --project workers/automation add claude-agent-sdk
# Pin the resolved version in pyproject.toml at implementation time; docs do not pin a version.
```

**Core imports**
```python
from claude_agent_sdk import (
    query,                 # one-shot headless call -> async iterator of messages
    ClaudeSDKClient,       # stateful client; ONLY this supports interrupt()/cancellation
    ClaudeAgentOptions,    # all config: model, max_turns, output_format, env, ...
    AssistantMessage, TextBlock, ResultMessage,
    tool, create_sdk_mcp_server, ToolAnnotations,  # only if we expose a submit tool
)
```

**Headless entry point (typed structured output via native json_schema)**
```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage
from jobhunter.domain.materials.analysis import JobAnalysis  # Pydantic model (Section 4b)

async def run_claude_draft(system_prompt: str, jd_snapshot: str) -> JobAnalysis:
    options = ClaudeAgentOptions(
        model="claude-opus-4-8",          # top model; effort defaults to "high" on Opus 4.8
        system_prompt=system_prompt,
        max_turns=None,                   # D-19: unbounded; nothing kills a healthy run
        # D-18/quality: no budget ceiling. (max_budget_usd exists; leave unset.)
        output_format={                   # NATIVE structured-output mode
            "type": "json_schema",
            "schema": JobAnalysis.model_json_schema(),
        },
    )
    structured = None
    async for message in query(prompt=jd_snapshot, options=options):
        if isinstance(message, ResultMessage):
            if message.subtype == "error_max_structured_output_retries":
                raise RuntimeError("Claude structured-output retries exhausted")
            structured = message.structured_output  # parsed dict matching the schema
    return JobAnalysis.model_validate(structured)   # second-line Pydantic validation
```

**Structured output:** native — `output_format={"type":"json_schema","schema": ...}`; the parsed object arrives on `ResultMessage.structured_output`. The SDK retries internally on schema-validation failure; exhaustion surfaces as `subtype="error_max_structured_output_retries"`. We still re-validate with Pydantic (defense in depth).

**Cancellation:** `query()` does NOT support interrupts. For cooperative cancellation (D-19) use `ClaudeSDKClient` as `async with`, call `await client.interrupt()`, then DRAIN `receive_response()` (the interrupted `ResultMessage` with `subtype="error_during_execution"` stays buffered) before reusing the client. For the parallel ensemble we wrap each SDK call in an `asyncio.Task` and cancel the task group on user cancel.

**No timeout / no turn cap (D-18/D-19):** `max_turns=None` (the default) = unbounded. Do not set `max_budget_usd`. Do NOT replicate the `claude_code_cli.py` 180s wall-clock deadline — that adapter exists for browser apply, not analysis.

**Auth (D-04):** the underlying Claude Code CLI uses the active Claude Code session credentials inherited from the process environment. No API key needed; do not inject one. Extra env (if any) goes through `ClaudeAgentOptions(env={...})`.

**Headless entry point (typed structured output via output_schema)**
```python
from openai_codex import AsyncCodex
from jobhunter.domain.materials.analysis import JobAnalysis

async def run_codex_draft(system_prompt: str, jd_snapshot: str) -> JobAnalysis:
    async with AsyncCodex() as codex:                      # reuses existing Codex login (D-04)
        thread = await codex.thread_start(
            model="gpt-5.5",                               # top current Codex model
            config={"model_reasoning_effort": "high"},     # max effort (D-18)
            sandbox=Sandbox.read_only,                     # analysis reads the JD; no FS writes
        )
        result = await thread.run(
            f"{system_prompt}\n\nJOB DESCRIPTION:\n{jd_snapshot}",
            output_schema=JobAnalysis.model_json_schema(), # JSON-schema-constrained output
            effort="high",
        )
        if result.status != "completed" or result.final_response is None:
            raise RuntimeError(f"Codex turn failed: status={result.status} err={result.error}")
        return JobAnalysis.model_validate_json(result.final_response)
```

**Structured output:** `output_schema=<json schema dict>` on `thread.run(...)` (also on `turn(...)`); the structured result is returned as text on `TurnResult.final_response` — parse with `JobAnalysis.model_validate_json(...)`. NOTE: docs name the param but do not pin the exact wrapper format for the schema — verify dict-vs-wrapper at implementation time.

**Invocation path from Python:** use the native `openai-codex` Python SDK directly — NO Node sidecar and NO CLI-subprocess wrapper like `claude_code_cli.py` are required. The SDK internally talks to the Codex app-server over JSON-RPC; that is an implementation detail behind `AsyncCodex`.

**No timeout / effort:** there is no documented turn/timeout cap to disable; `run()`/`turn()` are awaited to completion. Set `effort="high"` and `model_reasoning_effort="high"`. Cancellation = cancel the wrapping `asyncio.Task`.

**Auth (D-04):** "Existing Codex authentication is reused automatically" — the user's ChatGPT/Codex subscription login. Do NOT call `login_api_key(...)`; rely on the existing session. (`login_chatgpt()` / `login_chatgpt_device_code()` exist only for first-time setup, outside this worker.)

### Ensemble Orchestration (D-06 merge + synthesize — 3 legs)

**Common port (hexagonal).** One `AnalysisDraftPort` with three adapters (`ClaudeAnalysisAdapter`, `CodexAnalysisAdapter`, `AntigravityAnalysisAdapter`), each `async def draft(system_prompt, jd_snapshot) -> JobAnalysisDraft`. The use case depends on the port, never on a concrete SDK.

**Run 3 in parallel (asyncio), surface partial failures (failure mode #2).**
```python
import asyncio

async def run_ensemble(system_prompt: str, jd: str, adapters: list[AnalysisDraftPort]):
    results = await asyncio.gather(
        *(a.draft(system_prompt, jd) for a in adapters),
        return_exceptions=True,                 # NEVER let one failure cancel the others
    )
    drafts, failures = [], []
    for adapter, res in zip(adapters, results):
        (failures if isinstance(res, BaseException) else drafts).append(
            (adapter.model_id, res)
        )
    if not drafts:
        raise EnsembleError("all SDKs failed", failures)   # hard fail only if zero drafts
    # failures are PERSISTED as degraded-ensemble audit signal, not dropped (D-08)
    agreement = compute_agreement(drafts)                  # cross-model voting + fuzzy span match
    validated = validate_evidence_spans(drafts, jd)        # literal-substring check (D-15)
    canonical = await synthesize(system_prompt, drafts, agreement, validated)  # Claude leg, D-07
    return EnsembleOutcome(canonical, drafts, failures, agreement)
```

- `return_exceptions=True` is the key lever: it stops one SDK error/timeout from killing the healthy legs and gives the orchestrator both the wins and the losses to persist.
- **Where Pydantic + validators sit:** each adapter returns a Pydantic `JobAnalysisDraft` (schema-validated at the SDK boundary). `validate_evidence_spans` (deterministic, `rapidfuzz`/`difflib`-assisted but ultimately literal-substring per D-15) runs in the domain layer AFTER drafts are typed. The synthesizer (Claude Agent SDK, D-07) takes the typed drafts + agreement + validation report and emits the canonical `JobAnalysis`, which is Pydantic-validated and evidence-revalidated once more before persistence.
- **Synthesizer = Claude Agent SDK** (`run_claude_draft` variant whose prompt is "reconcile these N drafts honoring the agreement/validation report"), same native `json_schema` output mode.

### Common Pitfalls

1. **Assuming an "Antigravity SDK" exists.** It does not have a documented headless/library form (2026-06). Building the Google leg against an imagined SDK will block the phase. Use ADK/Vertex + Gemini 3 + ADC (or degrade to 2-SDK) — see SDK 3.
2. **Using `query()` then expecting to cancel it.** `query()` cannot be interrupted; only `ClaudeSDKClient.interrupt()` can. For per-leg cooperative cancel, wrap each call in an `asyncio.Task` and cancel the task — and remember `interrupt()` leaves the interrupted `ResultMessage` buffered (drain it).
3. **`asyncio.gather` WITHOUT `return_exceptions=True`.** Default `gather` cancels all siblings on the first exception — that would convert "one SDK failed" into "whole ensemble lost," directly causing failure mode #2 (silent partial ensemble). Always pass `return_exceptions=True` and persist the failures.
4. **Trusting the model's quoted evidence span.** Both SDKs can emit a schema-valid object whose `evidence_span` is paraphrased, not a literal JD substring (failure mode #1). Schema validation does NOT check grounding — the deterministic substring validator is mandatory and separate.
5. **Re-imposing a wall-clock timeout.** The `claude_code_cli.py` precedent has a 180s deadline; copying it here violates D-19. Analysis must run to completion; the only stop is cooperative cancellation.
6. **Caching by output instead of by input.** Reproducibility (D-11) comes from keying the cache on `snapshot_hash + prompt/SDK-set version` and reusing the canonical record — NOT from trying to make the stochastic ensemble byte-identical. Re-tailor must hit the cache, never re-reason.
7. **Codex auth confusion.** Calling `login_api_key(...)` introduces a metered key path the user explicitly rejected (D-04). Rely on the auto-reused existing Codex session; only the auth env/login state matters, not an `OPENAI_API_KEY`.

This is the "cache-as-repro-contract" stance: set effort/model deterministically, then trust the snapshot+version cache for stability.
- Pick the strongest current model per provider for a deep reasoning + extraction task; re-confirm the exact model id strings at implementation (model ids drift fast in 2025–2026).

**Core Pattern** (parallel drafts -> deterministic merge/validate -> Claude synthesizer -> cache+persist):
```python
# application/materials/analyze_job.py (sketch)
async def analyze_job(jd_snapshot: str, *, force: bool = False) -> EmployerAnalysis:
    cache_key = (sha256(jd_snapshot), PROMPT_VERSION, SDK_SET_VERSION)   # D-12
    if not force and (hit := repo.get_cached(cache_key)):
        return hit                                                       # D-11: reuse, never re-reason

    outcome = await run_ensemble(SYSTEM_PROMPT, jd_snapshot, [claude, codex, gemini])  # gather(return_exceptions=True)

    # Deterministic grounding gate on EVERY draft (failure mode #1)
    for model_id, draft in outcome.drafts:
        validate_evidence_spans(draft, jd_snapshot)        # literal substring (D-15) — rejects fabrication

    # Synthesizer reconciles typed drafts + agreement into the canonical record (D-06/D-07)
    canonical = await synthesizer.reconcile(
        SYNTH_PROMPT, drafts=outcome.drafts, agreement=outcome.agreement, jd=jd_snapshot,
    )
    validate_evidence_spans(canonical, jd_snapshot)        # re-validate the synthesized output

    record = EmployerAnalysis.build(
        canonical=canonical,
        per_model=outcome.drafts,        # D-08: persist all 3 sub-analyses
        failures=outcome.failures,       # D-08: persist degraded-ensemble signal (failure mode #2)
        agreement=outcome.agreement,
        cache_key=cache_key,
    )
    repo.save_versioned(record)          # D-13: supersede, never destroy prior accepted analysis
    publisher.publish(EmployerAnalyzed(...))
    return record
```

**Tool Use:**
- **No agent file/shell tools are needed.** This is constrained extraction, not autonomous coding. Keep `allowed_tools` empty for the Claude legs and `Sandbox.read_only` for Codex — the only "tool" is structured output. Do not grant Bash/Edit/Write; they add failure surface and non-determinism for zero benefit here.
- **Structured output is the contract, not a tool call.** Prefer each SDK's native structured-output mode (Claude `output_format=json_schema`, Codex `output_schema`) over a hand-rolled `submit_analysis(schema)` MCP tool. If a leg's native mode proves unreliable, fall back to a single forced `@tool("submit_analysis", JobAnalysis-schema)` Claude tool (Claude's-discretion lever from CONTEXT) — but native mode is the default.
- **Adapters consume existing auth only** (D-04): Claude Code session (Claude), reused Codex login (Codex), `GOOGLE_APPLICATION_CREDENTIALS`/ADC (Google leg). No new key management; no `login_api_key`, no `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` injection.

**State Management:**
- Canonical **DB rows** (D-09): `job_employer_analysis` (canonical) + per-model child rows + agreement/confidence + failure rows — never `metadata_json`. A single projection owner builds the read shape; TS↔Python projection parity test required (established repo pattern).
- **Versioning mirrors `MaterialsSet`** (D-13): a forced/failed re-analyze supersedes but never deletes the last accepted analysis — failed refreshes become audit history.
- **Cache** keyed on `snapshot_hash + prompt/SDK-set version` (D-12); re-tailor reuses the cached canonical record (ANALYSIS-06). Cache hit short-circuits the entire ensemble.
- Use-case owns the transaction and publishes `EmployerAnalyzed`; new `analyze_job` RPC (D-10) + auto `_run_analyze` sub-step of `tailor` (D-20) both route through the same use case.

**Context Window Strategy:**
- A single JD snapshot is small (typically << 10k tokens) and fits any leg's window with huge headroom (`claude-opus-4-8` = 1M tokens; Gemini 3 large; Codex ample). **No chunking, RAG, truncation, or summarization is needed for a draft leg** — pass the full snapshot verbatim so evidence spans stay literal substrings (truncation would silently break grounding, failure mode #1).
- The **synthesizer** receives N full typed drafts + the JD + the agreement/validation report. This is the largest prompt; it still fits comfortably in a 1M-token Opus window. If the draft set ever grew large, compact the agreement report (not the JD, and not the evidence spans) — never drop the JD the spans are validated against.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns for this 3-SDK structured-extraction ensemble.

### Structured Outputs with Pydantic

The schema is the contract for all three legs AND the synthesizer. One Pydantic model, fed to each SDK's native structured-output mode via `model_json_schema()`, then re-validated on the way out. Pydantic also encodes the grounding invariants the SDK schema cannot enforce.

```python
# domain/materials/analysis.py
from pydantic import BaseModel, Field, model_validator

class ReasonedKeyword(BaseModel):
    keyword: str
    evidence_span: str = Field(..., description="LITERAL substring of the JD snapshot (D-15)")
    requirement_ref: str | None = Field(  # D-17: links to the requirement it supports
        None, description="id of the parent requirement; None = orphan (allowed but flagged)")
    rationale: str
    is_orphan: bool = False

class Requirement(BaseModel):
    id: str
    text: str
    tier: Literal["must_have", "nice_to_have"]      # D-14: explicit tier
    weight: float = Field(..., ge=0.0, le=1.0)       # D-14: 0-1 priority within tier
    evidence_span: str

class JobAnalysis(BaseModel):
    role_framing: str
    inferred_seniority: str
    ideal_candidate_narrative: str                   # "what they're really looking for" (D-16)
    requirements: list[Requirement]
    keywords: list[ReasonedKeyword]

    @model_validator(mode="after")
    def _flag_orphans(self):
        valid = {r.id for r in self.requirements}
        for k in self.keywords:
            k.is_orphan = k.requirement_ref is None or k.requirement_ref not in valid  # D-17
        return self

class JobAnalysisDraft(JobAnalysis):
    model_id: str                                    # which SDK/model produced this draft
```

**Framework integration:**
- **Claude Agent SDK:** `output_format={"type":"json_schema","schema": JobAnalysis.model_json_schema()}`; read `ResultMessage.structured_output`; `JobAnalysis.model_validate(...)`.
- **Codex SDK:** `thread.run(..., output_schema=JobAnalysis.model_json_schema())`; `JobAnalysis.model_validate_json(result.final_response)`.
- **Google leg (Antigravity/Gemini):** the real `google-antigravity` SDK takes `response_schema` on `LocalAgentConfig` (passed the Gemini-adapted schema — `additionalProperties` stripped — serialised with `json.dumps(..., sort_keys=True)`); drain `response.chunks` then `await response.structured_output()`; `JobAnalysis.model_validate(...)`. Reference impl: `~/Github/mestre/mestre/vendor_lane/backends/antigravity_sdk.py`.
- **Grounding is NOT in the schema.** `evidence_span` being a *literal JD substring* (D-15) cannot be expressed in JSON Schema — it is enforced by the separate deterministic validator (`analysis_grounding.py`) after Pydantic validation. Schema-valid + Pydantic-valid + grounding-valid are three distinct gates.

**Retry logic:** native SDK retries handle schema-shape failures (Claude exhaustion → `error_max_structured_output_retries`). On top of that, the use case retries a leg up to **2 times** on (a) Pydantic `ValidationError` or (b) grounding-validator rejection (a span that is not a literal substring). Log each retry with `model_id`, the failing span/field, and the raw output. After 2 retries that leg is recorded as a **failure** (persisted per D-08), the ensemble proceeds with the surviving legs, and the degraded state is surfaced — never masked (failure mode #2). Surface to the user only when ALL legs fail.

### Async-First Design

- All three SDKs are async-native: Claude `query()`/`ClaudeSDKClient` are async iterators; Codex exposes `AsyncCodex`; ADK is async. The ensemble fan-out is `asyncio.gather(*legs, return_exceptions=True)` — the whole reason to be async here is true parallelism across providers (D-06).
- **The one common mistake:** calling `asyncio.run()` inside an already-running event loop. The Python worker / Temporal activity context is already async — call `await analyze_job(...)`, never `asyncio.run(analyze_job(...))` from within it. Use `asyncio.run` only at a true top-level sync entry point (e.g., a standalone CLI test harness).
- **A second async trap:** plain `asyncio.gather` (no `return_exceptions=True`) cancels healthy legs on the first failure — re-stated here because it is the mechanism behind failure mode #2.
- **Stream vs. await:** these legs need a fully-formed, schema-valid object to validate — **await the complete result**, do not consume partial streamed tokens for the canonical output. Streaming is useful only for live progress/audit events (tool-use / assistant-text lines, mirroring `claude_code_cli.py`'s event folding); the structured object is always taken from the final `ResultMessage`/`TurnResult`.

### Prompt Engineering Discipline

- **System vs. user separation:** the role/rubric/grounding rules live in the system prompt (`ClaudeAgentOptions(system_prompt=...)`; prepended for Codex); the user/turn content is ONLY the JD snapshot. Keep the JD verbatim and isolated so the model cannot confuse instructions with source text — and so evidence spans map cleanly back to the snapshot.
- **Grounding instruction is explicit:** instruct every leg that each `evidence_span` MUST be copied verbatim (a literal substring) from the JD, never paraphrased — this raises the pass rate of the deterministic validator even though the validator, not the prompt, is the real gate.
- **Few-shot:** inline 1–2 worked examples (a must-have with weight, a nice-to-have, a keyword tied to a span and a requirement_ref) directly in the system prompt — static, not dynamically retrieved (there is no corpus to retrieve from). Keep examples short to avoid biasing extraction toward the example's domain.
- **Token budget:** D-18 means no output ceiling, but still set generous EXPLICIT bounds in production where the SDK exposes them (Opus 4.8 max output is 128k) so a runaway generation can't hang indefinitely — "no ceiling" means high/unbounded by intent, not unset by accident. The synthesizer prompt is the largest; keep it structured (drafts as labeled JSON + a compact agreement report).
- **Prompt/SDK-set version is part of the cache key (D-12):** any prompt edit MUST bump `PROMPT_VERSION` so stale cached analyses are recomputed rather than silently served.

### Context Window Management

- **Drafts:** the single JD snapshot fits every leg's window with vast headroom (Opus 4.8 = 1M tokens). No chunking / RAG / truncation — pass the full snapshot so evidence spans remain literal substrings. Truncating the JD would silently break grounding.
- **Synthesizer:** receives N full typed drafts + the JD + the agreement/validation report — still comfortably within a 1M-token Opus window. If the draft set ever grows, compact the agreement report only; never truncate the JD or any evidence span.
- **No agent compaction is engaged:** these are short, bounded calls (constrained extraction with no tools), so the SDKs' auto-compaction never triggers — a deliberate consequence of keeping the legs tool-free.

### Cost and Latency Budget

- **Governing principle (D-18): cost is no object; quality is the only objective.** This section sizes the bill for awareness, NOT to drive optimization. Do not downgrade models or trim effort to save money.
- **Per-analysis cost estimate:** ~4 strong-model calls (3 drafts + 1 synthesis), each a few-k-token input + up to a few-k-token structured output, run at high effort. Order-of-magnitude **cents-to-low-dollars per uncached analysis** (Opus 4.8 at $5/$25 per MTok dominates; Codex/Gemini add to it). At single-user volume this is negligible — exactly why the quality-first stance is affordable.
- **Caching is the real budget control (and the repro contract):** the snapshot+version cache (D-11/D-12) means each JD is analyzed **once**; every re-tailor and re-open is a free cache hit. This is exact-match caching keyed on `snapshot_hash + prompt/SDK-set version` — NOT semantic caching (semantic/fuzzy cache hits would undermine the "same snapshot → same analysis" grounding guarantee). Use an explicit `force` flag to bypass.
- **No sub-task model routing / no cheaper models:** D-18 forbids cheaper-model substitution for any leg (the whole point is three strong, diverse models). The only "routing" is the cache short-circuit. The grounding validator and agreement computation are deterministic code (free, instant) — keep judgment in code, not in extra LLM calls.
- **Latency:** parallel fan-out means wall-clock ≈ slowest leg + synthesizer, not the sum. With no timeout (D-19) a slow high-effort run is acceptable; only cooperative cancellation stops it. Cache hits are effectively instant.

### Dimensions

| 6 | **Subtext capture without invention** (Section 1b "reading the subtext"; "seniority inference"; D-16) | **PASS:** the `ideal_candidate_narrative` + `inferred_seniority` capture the role's center of gravity and genuinely-implied core needs (e.g. "early team → ownership / ambiguity tolerance"), each still anchored to JD language; boilerplate ("fast-paced", "rockstar", EEO/benefits text) is NOT promoted to a requirement/keyword. **FAIL:** hallucinated subtext with no JD anchor, boilerplate mistaken for signal, or a seniority misread (staff/lead flattened to mid, junior read as senior) from over-indexing on one token. | **LLM Judge** (advisory; rubric from Section 1b) **+ Human** (edge cases) | **High** |
| 7 | **Keyword signal vs. ATS stuffing** (Section 1b "keyword signal"; ANALYSIS-03; Out-of-Scope: stuffing-to-score) | **PASS:** keywords are genuine screened-on skills/tools/quals, deduplicated, each tied to a real span and (where one exists) a `requirement_ref` a human recognizes as "the skills for this job". **FAIL:** every-noun bag, near-duplicate padding "to maximize match", soft-skill filler elevated to keywords, or keywords with neither evidence nor a parent requirement. | **Code** (dedup / orphan-rate / evidence-presence checks) **+ LLM Judge** (advisory: filler-vs-signal) | **High** |
| 8 | **Cross-model agreement** (signal, not pass/fail; D-06/D-08) | **PASS (signal healthy):** the persisted agreement/confidence across Claude / Codex / Gemini is recorded per run; high-agreement requirements/keywords are the trustworthy core. **LOW-AGREEMENT → FLAG:** requirements/keywords where the 3 legs diverge are flagged for review rather than dropped — divergence is first-class audit data, never silently resolved. | **Code** (compute + persist agreement; threshold flags low-agreement items) | **Medium (monitored signal)** |
| 9 | **EEO / protected-attribute hygiene** (Section 1b Regulatory) | **PASS:** the analysis never converts protected-class signals in a posting ("recent grad", "digital native", "young/energetic", gendered language) into a requirement or keyword. **FAIL:** any such phrase surfaced as a requirement/keyword or used to weight an "ideal candidate" attribute. | **Code** (denylist/regex screen of requirement+keyword text against EEO red-flag terms) **+ LLM Judge** (advisory: subtle cases) | **Medium** |

**Measurement-approach rationale (deterministic-first):** Dimensions 1–4 and the structural halves of 7–9 are fully deterministic and become the *shipping quality gate* (they run in unit tests + as online guardrails — Section 6). Dimensions 5, 6, and the judgment halves of 7/9 are genuinely subjective (must/nice realism, subtext, filler-vs-signal) and so use an LLM judge — but **uncalibrated this phase**, so they are ADVISORY signals surfaced for the user, never auto-blocking, per reference Pitfall 4. Calibration against the user (target ≥ 0.7 correlation) is the next-milestone harness work.

### Reference Dataset

**Status: OPTIONAL / starter — framed as the seed for the next-milestone harness, not a blocking deliverable this phase.** Begin building it *during* implementation (it doubles as integration-test fixtures), not after.

**Size:** **10–20 persisted JD snapshots** to start (reference guidance: 10–20 high-quality examples beat 200 mediocre ones). Real postings the user has actually encountered, captured as the exact persisted snapshot the ensemble reads.

**Composition** (cover critical paths + the Section 1b known failure modes):
- **Critical-path JDs (≈6–8):** clean, well-structured postings in the user's target field — the everyday case.
- **Boilerplate-heavy (≈2–3):** postings stuffed with "fast-paced / rockstar / wear many hats" + large EEO/benefits/"about us" sections — exercises boilerplate-as-requirement and Dimension 9.
- **Must/nice trap (≈2–3):** long aspirational qualifications lists mixing hard gates (clearance, hard YOE bar, required degree) with "preferred / a plus" — exercises Dimensions 5 and wishlist inflation.
- **Seniority edge (≈2):** a staff/lead/principal posting and a junior posting whose level must be read from scope/ownership language, not a single salient token — Dimension 6.
- **Grounding adversarial (≈1–2):** vague postings ("cloud experience", "modern tooling") that tempt over-inference into concrete fabricated requirements (Kubernetes, a specific framework) — the literal-substring trap for Dimension 1.

**Labeling:** For deterministic dimensions (1–4, structural 7/9) labels are **automated** — the validators compute pass/fail against the snapshot, no human labels needed (this is why they ship now). For subjective dimensions (5/6, judgment 7/9) the **single user (product-owner = operator/beneficiary)** is the standing domain expert of record (Section 1b table): the user records the gold must/nice split, priority ranking, "real keywords", and seniority read for each starter JD, adjudicating LLM-judge disagreements. External technical-recruiter / hiring-manager / resume-coach calibration is *desirable but not assumed* at single-user scope; capture it opportunistically and defer formal calibration to the next milestone.

## 6. Guardrails

> **Guardrail vs. flywheel test:** "if this goes wrong, is it catastrophic?" Fabrication, schema breakage, and a silent partial ensemble corrupt the single source of truth → **online guardrails** (run at generation time, before persistence). Quality drift (must/nice realism, subtext, keyword fidelity, agreement trends) is a quality signal → **offline flywheel** (sampled, advisory).
>
> **No cost/latency guardrails.** Per D-18/D-19 cost is no object and there is NO wall-clock/turn cap — the ONLY stop is cooperative cancellation. Do not add any guardrail that caps tokens, caps turns, or kills a run on a time/cost threshold. The online guardrails below are *correctness* gates that re-ask or flag; none of them aborts a healthy run on a budget.

### Online (Real-Time — run on every analysis at generation time, before persistence)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Grounding validator** (cardinal — Dimension 1, D-15) | Any `evidence_span` on any draft or the synthesized canonical is NOT locatable in the JD snapshot under the normalized substring + snap-to-source matcher (its WORDS are absent — a paraphrase/synonym/hallucination, not merely a formatting difference). | **Block + re-ask.** Reject that leg's output and retry the leg up to 2× (Section 4b retry policy). On continued failure the leg is recorded as a **failure** (audit row) and the ensemble proceeds on surviving legs — never persist a fabricated span. Located spans are **snapped** to verbatim JD text. The synthesized canonical is re-validated + snapped; a grounding failure there blocks persistence and triggers a synthesizer re-ask. |
| **Schema + invariant validator** (Dimension 2) | Pydantic `ValidationError`, `weight` ∉ [0,1], a tier missing, or an unresolved `requirement_ref` not flagged orphan. | **Block + re-ask.** Native SDK structured-output retry first; then the use case re-asks the leg up to 2×; persistent failure → leg recorded as failure, ensemble continues on survivors. |
| **Partial-ensemble surfacing** (Dimension 3, D-08) | Any leg errors / times out / malforms (caught by `asyncio.gather(return_exceptions=True)`). | **Flag (never drop).** Persist the failure (`model_id`, error, raw output) + record `ensemble_completeness`; surface the degraded state on the record. Hard-fail to the user ONLY if ALL legs fail (`EnsembleError`). A degraded ensemble is published, clearly marked degraded — never masked as full confidence. |
| **EEO red-flag screen** (Dimension 9) | A requirement or keyword text matches the protected-attribute denylist ("recent grad", "digital native", "young/energetic", gendered terms, etc.). | **Block from the requirement/keyword set + flag.** Drop the offending item from requirements/keywords (it must not become something to satisfy) and record the screen hit as an audit note. Does not abort the run. |
| **Cache-contract gate** (Dimension 4, D-11/D-12) | An `analyze_job` arrives for an existing `(snapshot_hash, PROMPT_VERSION, SDK_SET_VERSION)` and `force=False`. | **Short-circuit (serve cached canonical).** Bypass the ensemble entirely and return the persisted record — the reproducibility guarantee. Prevents silent re-reasoning/drift on re-tailor. |

### Offline (Flywheel — sampled, advisory; feeds the next-milestone harness)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Cross-model agreement trend** (Dimension 8) | Every analysis records agreement/confidence; review the aggregate trend + any run with low whole-analysis agreement. | Falling agreement (3 legs diverging more over time) → investigate prompt/model drift; bump `PROMPT_VERSION` if a prompt fix lands (forces recompute). Per-item low agreement is already flagged inline for the user. |
| **Must/nice & priority realism** (Dimension 5, LLM-judge advisory) | Smart sampling — weight toward runs the deterministic gates passed but the LLM judge flagged (judge↔code divergence), plus runs the user manually re-tailored. | Persistent wishlist-inflation or flat-weight patterns → refine the system-prompt rubric/few-shot, bump `PROMPT_VERSION`. Feeds rubric calibration for the next-milestone harness. |
| **Subtext / boilerplate-as-signal** (Dimension 6, LLM-judge advisory) | Sample boilerplate-heavy and early-team/staff JDs; review narrative + flagged-boilerplate audit data. | Recurrent boilerplate-promoted-to-requirement or seniority misreads → strengthen the boilerplate-filtering + scope/ownership prompt guidance; add the offending JD to the starter reference set. |
| **Keyword fidelity vs. stuffing** (Dimension 7) | Track per-run keyword count, dedup rate, and orphan-keyword rate; sample high-count / high-orphan runs. | Rising bag-of-nouns / near-duplicate padding / orphan rate → tighten the keyword prompt + dedup logic; this is the explicitly-rejected stuffing failure (REQUIREMENTS Out-of-Scope). |
| **Reproducibility drift on forced recompute** (Dimension 4) | When the user issues `force=True`, log the set-overlap (Jaccard of must-haves / keywords) vs. the superseded canonical. | Must-have overlap dropping below ~0.8 across forced recomputes → the analysis is unstable; investigate model/prompt change and treat as a regression signal before the next milestone formalizes it. |

## 7. Production Monitoring

> "Production" here = the single-user local-first runtime. Monitoring is the existing Langfuse/OTEL trace layer plus the persisted audit trail (per-model drafts + agreement + failures + `ensemble_completeness`), which is itself the durable monitoring record the user inspects. No new platform, no paging infra — "alerts" are local signals surfaced to the operator.

**Tracing Tool:** **Langfuse via OpenTelemetry — the existing wiring** (`workers/automation/src/jobhunter/infrastructure/observability/`; `docs/architecture.md` §Observability). The worker already exports spans over OTLP/HTTP to Langfuse (`init_otel()`, `llm_generation_span(...)`). **Do NOT introduce Arize Phoenix or any other platform.** Instrument the new ensemble into this same pipeline:

- Each of the 3 draft legs + the synthesizer → a `langfuse.observation.type=generation` span via the existing `llm_generation_span(...)` helper (sets `gen_ai.request.model` / `gen_ai.response.model` and, where the SDK exposes them, `gen_ai.usage.*_tokens` — recorded for awareness only; D-18 means tokens never gate anything).
- The `_run_analyze` sub-step → a `pipeline.stage.analyze` span (matching the existing `pipeline.stage.<stage>` convention) plus `StageStarted` / `StageCompleted` / `StageFailed` `event` observations + `job_events` rows, so a long high-effort run (no timeout, D-19) stays visible via SSE/recent-activity before the JSON-RPC call returns.
- The `analyze_job` RPC (D-10) → the existing `rpc.<method>` dispatch span.
- The deterministic gates (grounding, schema, EEO screen) and the agreement computation → span attributes / `event` observations on the analyze span so a block/re-ask/flag is traceable to the run.

**Auth/config:** reuse `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` / `LANGFUSE_BASE_URL`; `LANGFUSE_DISABLE=1` opts out; missing creds degrade to no-export with a warning (worker continues). No new credentials.

**Key Metrics to Track:**
1. **Grounding rejection rate** — fraction of draft spans rejected by the literal-substring validator (per leg + canonical). The cardinal-failure pulse; spikes mean a model started fabricating or a prompt regressed.
2. **Ensemble completeness** — legs succeeded / legs attempted per run, and the per-leg failure rate by `model_id`. Detects a degraded ensemble (failure mode #2) and an unhealthy SDK/provider.
3. **Cross-model agreement / confidence** — the persisted whole-analysis agreement score and the count of low-agreement (flagged) items per run. The "are the 3 models converging" quality signal.
4. **Cache hit rate** — fraction of `analyze_job` calls served from the snapshot+version cache vs. recomputed. Confirms reproducibility/reuse (ANALYSIS-05/06) is actually happening on re-tailor.
5. **Schema/invariant + EEO-screen reject counts** — re-ask volume on schema failures and items dropped by the EEO red-flag screen. Secondary correctness pulse.

> Deliberately NOT primary metrics: latency and cost/tokens. They are recorded on spans for awareness (D-18 cost no object) but never alerted on and never used to optimize or cap — see Section 6.

**Alert Thresholds** (local signals to the operator, not paging):
- **Grounding rejection rate > 0** on the *canonical* (synthesized) record after re-ask → block already fired (Section 6); surface prominently — a fabricated span reached synthesis. Any sustained rise in *draft-leg* rejection rate → investigate the offending model/prompt.
- **Ensemble completeness < 3/3 (degraded)** → mark the analysis degraded in the read model; **= 0/3 (all legs failed)** → hard error surfaced to the user (`EnsembleError`).
- **Whole-analysis agreement below a calibrated floor** (start ~0.5, tune against the starter set) → flag the analysis for user review; do not block.
- **Cache hit rate unexpectedly low on re-tailor** (a re-tailor that should have hit the cache recomputed) → investigate cache-key/versioning bug — a reproducibility regression (failure mode #3).
- **Any EEO red-flag screen hit** → surface as an audit note for the user (low volume, always worth a look).

**Smart Sampling Strategy** (which runs the single user reviews — weight toward concerning signals, per reference guidance):
- **Judge↔code divergence:** runs that PASSED all deterministic gates but the advisory LLM judge flagged on must/nice realism, subtext, or keyword fidelity — the highest-signal sample and the seed for next-milestone judge calibration.
- **Degraded ensembles:** any run with `ensemble_completeness < 3/3`.
- **Low agreement:** runs/items below the agreement floor.
- **User-initiated `force` recomputes:** the user already signaled distrust; review the set-overlap vs. the superseded analysis.
- **Boilerplate-heavy / seniority-edge / adversarial JDs:** route these (from the starter reference composition) preferentially into review since they exercise the known domain failure modes.
