# Phase 8 Plan 03 - Shell Behavior And Persistence Tests

## Goal

Add focused automated tests proving Phase 8 did not change shell behavior, preference persistence seams, route navigation, or connection-status accessibility while changing chrome styling and icons.

## Requirements Covered

- LAYOUT-01: route behavior and user workflows remain unchanged.
- LAYOUT-02: font token wiring remains intact.
- LAYOUT-04: density modes continue to affect shell row height.
- LAYOUT-05: readable shell surfaces are proven through computed-style assertions and browser proof.

## Tasks

1. Add layout component tests if coverage is missing.
   - Render shell controls with existing provider/router test harness patterns.
   - Verify global search ignores blank queries.
   - Verify non-empty Enter navigates to `/jobs` with trimmed `q` and `page=1`.
   - Verify density select exposes compact, regular, comfy and updates the store.
   - Verify theme toggle accessible name changes after click.

2. Add connection status accessibility tests if feasible with existing harnesses.
   - Preserve `aria-live="polite"` on the pill.
   - Preserve `role="alert"` for worker-unhealthy banner.
   - Preserve `role="status"` for long-disconnected banner where timers can be controlled deterministically.
   - Do not start a real worker or SSE stream just to force status states.

3. Add persistence/pre-paint contract tests only if needed.
   - If implementation changes `ui-preferences`, assert key `jh:ui-preferences`, version `1`, and state shape remain compatible.
   - If `index.html` changes, assert the pre-paint script still reads the Zustand persist shape and writes `data-theme`.

4. Extend static token contract tests for shell/font assertions.
   - Assert font imports and mappings remain present.
   - Assert density selectors remain on `.app-shell[data-density]`.
   - Assert shell chrome selectors consume semantic tokens if CSS changes are substantial.

## Acceptance Criteria

- Automated tests prove global search, theme, density, and connection accessibility behavior after visual changes.
- Tests use synthetic state and do not touch user data, local databases, workers, browser profiles, or generated artifacts.
- Existing harness/provider patterns are reused; no direct platform calls are added to shell code.

## Risks And Guards

- Risk: tests couple to TanStack Router internals. Guard: prefer user-visible URL/result assertions and existing `createMemoryHistory` harness patterns.
- Risk: connection tests become timer-flaky. Guard: test immediate worker-unhealthy state first; only test long disconnect with controlled fake timers if stable.
- Risk: persistence tests overreach into implementation details. Guard: assert the documented storage key/version/shape because `index.html` depends on it.
