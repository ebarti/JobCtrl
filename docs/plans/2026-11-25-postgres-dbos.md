# Local PostgreSQL and DBOS migration

The target is a local desktop with a PostgreSQL database per workspace containing both application tables and DBOS system tables. The supported upgrade source is the current owner's Python workspace. The source SQLite files and owned artifacts survive migration. Public HTTP, CLI and browser operations retain their identities, accepted data and observable outcomes.

## Delivery and integration

1. Freeze the starting schema and inventory. Use a private SQLite online backup for the actual upgrade rehearsal. Inventory tables and keys, source attachments, file references, history, active actions and unresolved receipts. Store no personal contents in source control or published evidence. Preserve the original workspace and rehearse only against a disposable isolated target. Keep live writers on the old workspace until final cutover.
2. Establish the PostgreSQL connection, workspace identity and native schema. Use one transaction for all writes across public feature boundaries. A caller-owned SQLAlchemy connection is available to DBOS. Port SQL and preserve observable sort, filtering, event cursors, uniqueness, and feature removal behavior. Explicitly serialize contested admissions, revisions and budget reservations. Exercise simultaneous writers on the same job or model lane.
3. Add a one-way, repeatable import of the currently used Python schema. Read a consistent snapshot. Create and validate a staged destination, copy canonical values and all generated keys, verify constraints, per-table counts and deterministic content digests, and advance identity sequences. Validate workspace bindings and artifact references. Store migration status privately and permit retry following interruption. Preserve completed action history as product records. Drain or explicitly reconcile outstanding work. Pending external effects and provider charges retain uncertainty. Verify before marking the destination active. Preserve the source for rollback and distinguish rollback before and after subsequent writes.
4. Use DBOS durable queues and stable workspace/action identities. Persist domain acceptance and dispatch atomically on the same PostgreSQL connection. Preserve action status, cancel, lost acknowledgement, schedules, worker version/workspace fencing and resumability. Keep recurring searches for new jobs, and keep saved-posting rechecks manual. Preserve at-most-once external submission and accepted artifacts on failed refreshes.
5. Model Discovery as one durable search across pages. Commit page identities, remaining limit, cursor, source cooldown and pending assessment handoffs together. Keep work for other jobs running while a board waits. Use stable job and source revision identities, reuse billed model results and shared requirement qualifications, and allow retry of an individual eligible job through the UI. Distinguish received, duplicate, excluded, saved, and pending outcomes. Synthetic external boundaries own verification.
6. Integrate the desktop and development stack. Resolve a private local PostgreSQL endpoint for the selected workspace. Provision and control only the selected local server, verify worker/build readiness, replace Temporal packaging and diagnostics, and provide a coherent PostgreSQL backup and restore. Verify real startup, shutdown and restart. Preserve workspace files, credentials, accepted artifacts and unresolved usage receipts.
7. Qualify the integrated checkout. Run real PostgreSQL and DBOS through HTTP/CLI/browser with controlled external services. Verify concurrent admissions, crash before and after enqueue, worker replacement, retry, cancellation, cooldown and schedules. Validate the built native lifecycle, package contents, basic backup/restore, static checks and product browser journeys. Rehearse migration of the owner's private snapshot without starting background work or contacting providers. Compare source and target aggregates without exposing their contents. A real cutover uses a fresh final snapshot and verified source/target identities.

## Release boundary

Older schema generations and replaying old Temporal histories are outside this upgrade contract. Preserve the original history files and in-app completed action records. Record the tested candidate, failures, independent review and actual execution separately. A source candidate, live local upgrade and public release are distinct delivery states.
